# Technical Decisions

This log records material technical and methodological decisions made during Question 1 implementation.

| Date | Decision | Options Considered | Selected Approach | Justification |
|---|---|---|---|---|
| 2026-07-30 | Settlement identifier strategy | `settlement_id`; settlement name | Use `settlement_id` as the primary settlement reference key. | The completed audit recorded zero duplicate `settlement_id` values in the settlement masterlist. |
| 2026-07-30 | Data quality handling | Remove anomalous records; preserve and flag anomalous records | Preserve anomalous records and flag them rather than silently removing them. | The completed audit identified GPS missing values, e-Tally missing values, and potentially suspicious dose rows that require documented review. |
| 2026-07-30 | Spatial database architecture | File-only workflow; PostgreSQL/PostGIS spatial database | PostgreSQL/PostGIS with `reference`, `raw`, `processed`, and `audit` schemas. | Separates supplied source records, reference geography, derived evidence products, and idempotent ingestion audit records while preserving geometry in EPSG:4326. |
| 2026-07-30 | Local development database environment | Local PostgreSQL/PostGIS installation; Dockerized PostgreSQL/PostGIS | Dockerized PostgreSQL/PostGIS | Ensures reproducible spatial database setup. |
| 2026-07-30 | GPS ingestion strategy | File-based loading without registry; checksum-based idempotent ingestion | Checksum-based idempotent ingestion into PostGIS raw layer | Maintains traceability and prevents duplicate loading. |
| 2026-07-30 | GPS quality assessment strategy | Delete flagged points; preserve and flag points | Preserve raw points and write documented quality flags to a separate processed table. | Enables review of uncertainty and prevents undocumented data loss. |
| 2026-07-30 | Threshold selection process | Undocumented fixed rules; documented provisional thresholds | Use documented provisional thresholds with explicit limitations and review before downstream interpretation. | Assessment requirements require defended thresholds; current thresholds are operational screening rules, not final evidence of error. |
| 2026-07-30 | Python project organization | Notebook-only implementation; reusable package modules consumed by notebooks | Reusable `src` package consumed by notebooks. | Improves maintainability and reproducibility. |
| 2026-07-30 | Settlement attribution scenarios | One undocumented buffer; fixed and sensitivity scenarios | `baseline_30m`, `sensitivity_60m`, and urban accuracy-aware attribution in EPSG:32632. | The 30 m baseline aligns with QA screening; the 60 m ceiling covers the observed 58 m maximum reported accuracy while remaining below typical settlement spacing. |
| 2026-07-30 | Visit evidence reconstruction | Single proximity point; sustained team/date evidence | Require a non-ambiguous episode with at least 3 eligible points, 15-minute dwell, and no internal gap above 15 minutes. | The logger records approximately every 60 seconds; sustained continuity prevents isolated proximity points from being classified as visits. |
| 2026-07-30 | Reference-data loading workflow | Load source files inside the attribution notebook; dedicated ingestion command | Load boundaries and settlements through a standalone idempotent ingestion command before Notebook 03. | Keeps source loading transaction-safe and testable, while the notebook uses only database-resident inputs. |
| 2026-07-30 | Operational attribution estimate | Treat all scenarios as equivalent; select a documented primary estimate | Use `baseline_30m` as the primary operational estimate and retain 60 m and urban accuracy-aware results as sensitivity analysis. | Validation found 139 visited settlements at 30 m, 171 at 60 m, and 142 under urban accuracy-aware attribution (revised 2026-07-31; originally 214/241/216 before the fixes documented below — see the 2026-07-31 rows for the full defect-and-correction narrative). |
| 2026-07-30 | Coverage decision source | GPS only; e-tally only; reconciled product | Present the reconciled baseline GPS and e-tally product. | GPS is stronger evidence of physical presence; e-tally is stronger evidence of reported service delivery and dose quantities. The gap between them (73.26 percentage points; revised 2026-07-31, originally 70.34) requires rapid verification, and its size is itself an argument that this most likely reflects an attribution/data-completeness limitation rather than a literal 5.43% service-delivery rate — see the Incident Manager brief. |
| 2026-07-30 | Primary missed-settlement weights | Broad distance band; k-nearest neighbours | Binary, row-standardized k=8 KNN weights in EPSG:32632. | k=8 has zero islands and one connected component while retaining a local neighbourhood definition; the broad 9,050 m band is retained only for sensitivity. |
| 2026-07-30 | Local cluster inference | Raw local p-values only; multiple-testing correction | Retain raw permutation p-values and use Benjamini-Hochberg FDR-adjusted significance for primary labels. | Thousands of local tests require explicit multiple-testing control; raw results remain available for transparent operational screening. |
| 2026-07-30 | Requirement 5 operational interpretation | Present raw local patterns as hotspots; use corrected inference | Treat the positive Global Moran result as evidence of overall spatial concentration, while retaining no confirmed local clusters after FDR correction. | The primary Global Moran p-value was 0.026 (revised 2026-07-31, originally 0.001), still significant at alpha 0.05; no Local Moran test remained significant after multiple-testing correction, before or after the revision. The ambiguity-included sensitivity scenario, unlike the other two, is no longer significant at all after the revision (p=0.140) — reported plainly rather than omitted, since it is a genuine result of the correction, not a modelling choice. |
| 2026-07-30 | Operational evidence confidence | Treat GPS absence as missed settlement; distinguish evidence and inference | Use high, moderate, low, and unknown confidence labels for observed evidence and recommendations. | GPS absence can result from operational failure or data artefacts; it is not proof of non-performance. |
| 2026-07-30 | Mop-up recommendation | Deploy directly from a single evidence source; verify reconciled disagreements | Prioritize rapid verification and data/device reconciliation before mop-up or performance action. | GPS supports presence and e-tally supports reported delivery; neither alone proves both. |
| 2026-07-31 | GPS raw-data structural defect (defect 1 of 3) | Leave unaddressed and undocumented; add a documented QA rule and re-run the pipeline | Added `source_file_date_mismatch` as a seventh QA rule (`src/quality/gps_quality_rules.py`) and excluded flagged points from settlement attribution (`src/attribution/settlement_attribution.py`). | Full-file inspection found that although the data pack names each file for one team, one day, the files actually contain 6–21 days of continuous, one-point-per-minute logging beyond their nominal day (104 of 160 files affected; 85.5% of all 956,702 raw points fall outside their own file's nominal day). For 66 of 160 team-days, two different sibling files both contributed points during real duty hours on the same real campaign date — e.g. Team 1 on 10 March had simultaneous GPS fixes roughly 70 km apart — which is physically impossible and was silently corrupting settlement attribution. Restricting each point to its own file's nominal day is a direct, deterministic consequence of the data pack's own stated "one file per team per day" structure, not a judgement threshold. |
| 2026-07-31 | Speed-calculation unit-conversion bug (defect 2 of 3) | Leave `calculated_speed_kmh` as coded; add the missing metres-to-kilometres conversion | `src/quality/gps_quality_rules.py`'s `calculated_speed_kmh` divided distance in metres directly by elapsed hours, producing metres-per-hour while being compared against an 80 km/h threshold — a flat 1000× inflation. Added the missing `/1000.0`. | Found while re-verifying the first fix: after fixing defect 1, the visited-settlement count did not move at all (stayed at exactly 50), which was suspicious given how much data had changed. Hand-verified on a genuinely clean point (Team 1, 09:00 on the real first campaign day, walking-pace movement between fixes): the buggy formula computed 6,349.56 km/h for a movement that is correctly 6.35 km/h. This one bug alone had been flagging 36.2% of all points as `impossible_speed` since the original 2026-07-30 build, independently of the file-date defect. |
| 2026-07-31 | Sequence-computation contamination (defect 3 of 3) | Leave gap/speed/stationary-cluster rules chaining across contaminated points; scope them to same-file-day points only | `evaluate_gps_quality` now computes `source_file_date_mismatch_flag` first, then restricts every sequence-dependent computation (previous point, time gap, calculated distance/speed, stationary-cluster chaining) to only the points that pass that check — implemented in `evaluate_gps_quality` and `_mark_stationary_clusters`. | Fixing defect 2 alone still left `impossible_speed` at 22.6% of all points, and legitimate near-settlement points were still overwhelmingly flagged (83% in one spot check) even with the correct formula. The cause: a legitimate point's "previous point" was still being drawn from the same contaminated global per-team/logger timeline defect 1 identified, so two physically unrelated fixes from different real tracks could still be chained together and produce a genuine (not a units-bug) large calculated speed between them. Scoping the sequence to same-file-day points dropped `impossible_speed` to 0.59% of all points — a rate consistent with genuine occasional GPS noise, not systemic contamination. |
| 2026-07-31 | Stale quality-flag accumulation (defect 4, found during verification) | Leave `upsert_quality_flags` as an insert/update-only upsert; make it a full replace | `upsert_quality_flags` now runs `DELETE FROM processed.gps_quality_flags` before writing the freshly computed flag set, instead of only inserting or updating rows present in the new batch. | While re-verifying defect 3's fix, direct attribution and reconciliation queries showed 55 visited settlements, but the notebook-written CSV outputs still showed 50 — and a direct check found `impossible_speed`-flagged rows in the database with `created_at` timestamps spanning nearly two hours across three different QA re-runs (346,610 rows, close to the *original* buggy count) despite the corrected computation itself producing only 5,612. The upsert only ever inserted or updated rows present in the current run's flag set; it never removed a row for a point that had stopped being flagged since a previous run. Every iterative fix in this session had therefore been silently re-polluted by its own predecessor's stale flags. This is why the 50 and then 55 figures reported earlier in this correction were themselves still wrong — the true, fully-clean figure is 139 visited settlements at the 30 m baseline, computed only after this fourth defect was also fixed and the whole pipeline re-run one final time against a genuinely clean `gps_quality_flags` table (verified: single `created_at` value across all 2,023,508 rows, 5,612 of them `impossible_speed`). |
| 2026-07-31 | A3 map statistic box, fifth hardcoded-value defect | Leave the map's Global Moran's I box hardcoded; read it from the executed output at generation time | `src/cartography/generate_a3_pdf.py` now reads the primary scenario's Global Moran's I, expected I, z-score, and p-value from `outputs/tables/global_moran_summary.csv` at generation time via a new `_primary_global_moran()` helper, instead of three hardcoded literal strings; the cartographer credit line's date is now `date.today()` rather than a fixed string. | Regenerating the map after the first GPS fix produced a map whose visible evidence classes were correct but whose "Global spatial statistic" box still showed the pre-fix I=0.046612/p=0.001 figures untouched — the same class of silent-staleness defect as the notebook 04 hardcoded reconciliation summary, independently found by inspecting the regenerated PDF rather than assuming it was correct because it rendered without error. |
| 2026-07-31 | Final verified state | Report an intermediate figure as final; verify DB and every output file agree before reporting anything as final | After fixing all five defects above, every stage was re-run once more in strict sequence (no overlapping commands), and the database state was checked directly against every regenerated CSV, notebook, and document before any of them was treated as authoritative. | Two earlier corrections within this same session (50 visited, then 55 visited) were each reported as final before the stale-flag-accumulation defect was found, and both were wrong. The lesson applied here: a pipeline re-run is only as trustworthy as its most stateful component, and a table that "upserts" is not automatically idempotent under changing rule logic. |
| 2026-07-31 | Idempotency claim without an automated test | Leave the "running it twice must not duplicate records" requirement (Q1 requirement 1) as a documented log-behaviour claim only; add an executable test | Added `tests/test_gps_ingestion_idempotency.py`: re-ingests a real data-pack file twice and asserts the raw row count is unchanged and the second run reports itself as skipped, and separately asserts that a same-named file with different content is rejected rather than silently accepted. `pytest` added to `environment.yml`. | This gap was flagged in a prior audit of Q1 and left open; given the amount of re-ingestion this same defect-fix session performed, an assertion this central to requirement 1 warranted a real, executed check rather than continuing to rely on reading log output. Verified passing (2 passed) against the live database with no change to raw row counts or the ingestion registry afterward. |
