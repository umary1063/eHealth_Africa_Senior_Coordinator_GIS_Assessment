# Serving a 2,524-row settlement list to a 2GB tablet

Q3 requirement 6.

## The mechanism used: cascading `select_one_from_file`, not an embedded choice list

`lga` (4 rows), `ward` (40 rows, filtered by `lga_code=${lga}`) and `settlement` (2,524 rows,
filtered by `ward_code=${ward}`) are declared in `form/HH2026_v1.xlsx` as
`select_one_from_file lgas.csv` / `wards.csv` / `settlements.csv`, with the CSVs attached as form
media rather than typed into the XLSForm's own `choices` sheet. `choice_filter` narrows each list
to the parent's selection before the enumerator ever sees it, so in practice the settlement picker
only ever has to render the handful of settlements in the selected ward (Bansara's 40 wards
average 63 settlements each; the largest ward is nowhere near 2,524).

This is the same name/label CSV schema already used in `reference_media/lgas.csv`,
`wards.csv`, `settlements.csv` — copied into `form/media/` unmodified, so the settlement register
supplied in the data pack is the settlement register served in the field, with no intermediate
transformation step that could silently drop or relabel a settlement.

## Why this, and not the alternatives

**Rejected: put all 2,524 settlements in the XLSForm `choices` sheet.** This is the "choices
worksheet" the question paper explicitly says is not an acceptable answer, and it is worth being
concrete about the *mechanism* of the failure, not just citing the instruction: every row in the
`choices` sheet is compiled by pyxform into an `<itext>` translation entry *and* an `<item>` node
inside the XForm's primary `<instance>`, for every declared language. With two languages
(English, Hausa) and the settlements list alone, that is roughly 5,000 `<item>` nodes plus 5,000
`<itext>` text nodes parsed into memory and held for the lifetime of the form on a device with
2 GB total RAM shared with the OS, ODK Collect itself, and every other open form. ODK Collect's
own documentation and forum guidance flag exactly this pattern (multi-thousand-row inline choice
lists) as a common cause of out-of-memory crashes and multi-second render stalls on low-end
Android hardware — the two failure modes the operating conditions are explicitly warning against
(2 GB devices, up to 9 days of continuous field use per device without a restart-and-recover
opportunity via reinstall/re-provisioning).

**Rejected: `itemsets.csv` / the legacy `search()`-only external-selects mechanism.** This
predates `select_one_from_file`, requires a specific flattened itemset file format generated by a
separate conversion step, and has been superseded in current ODK tooling by
`select_one_from_file`, which needs no extra generation step and consumes the reference CSVs as
supplied. Using the deprecated path would add a build step with no offsetting benefit.

**Rejected: a live server lookup (REST API/typeahead against Central).** The operating conditions
state no network coverage for up to 9 consecutive days; any design that assumes connectivity
during the interview is unusable for most of the fieldwork period.

**Rejected: reduce the list before shipping (e.g. only the settlements in the enumerator's own
ward).** This would need a per-enumerator, per-day form variant, which conflicts with requirement
10 (one form version in the field per device, tracked by `formVersion`, not per-enumerator
custom builds) and would break the moment an enumerator is reassigned.

## How `select_one_from_file` actually avoids the memory problem

The CSV is not parsed into the form's own instance at load time. ODK Collect indexes the file
once (on first use) and performs indexed lookups against it as the enumerator types into the
`search()`-driven autocomplete box and as `choice_filter` is evaluated — it is closer to a
lightweight on-device database query than to an in-memory list. This is why the same technique is
used for `staff_roster.csv` lookups (`pulldata()`, Section 1) and `previous_round_households.csv`
existence checks (question 1.13) — those files are read on demand at the moment a specific value
needs to be looked up, not loaded wholesale into the running form.

## What was NOT changed

`settlements.geojson` was deliberately not used as the choice source, even though it carries the
same 2,524 points. Its schema (`id`/`title`/`ward_code`/`ward_name`/`lga_name` — no `lga_code`, no
`name`/`label` pair) does not match what `select_one_from_file` expects, whereas `settlements.csv`
already carries `name`/`label` columns matching ODK's convention exactly, plus the `lga_code` /
`ward_code` keys the cascade needs. `settlements.csv` is treated as authoritative for the form;
the GeoJSON is left for GIS/mapping use outside the form (Q1/Q2 of this assessment), which is
consistent with the common data-pack instruction that "where two files disagree, neither is
automatically authoritative — decide, and say why."
